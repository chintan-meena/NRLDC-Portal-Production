## 3. Bugs

### BUG-1 — Cross-region plant assignment / transfer
- **Severity:** HIGH  ·  **Area:** Region isolation / plant ownership  ·  **Status: FIXED & re-verified**

**Preconditions:** Two regions with an admin each; an RE plant registered in region B (e.g. `REWIND2`
in ERLDC); a QCA account in region A (e.g. `alpha@nrldc`).

**Steps to reproduce (pre-fix):**
1. As the **NRLDC** admin, `POST /api/users/alpha@nrldc/assignments` with `{ wbes_acronym: "REWIND2",
   from_date: "2025-03-01" }` — where `REWIND2` belongs to **ERLDC**.
2. Observe the response and then check the plant from the ERLDC side.

**Expected:** The plant belongs to ERLDC; an NRLDC admin must not be able to assign or transfer it.
The request should be rejected (403).

**Actual (pre-fix):** `201 { status: "Assigned" }`. The ERLDC plant was directly assigned to an NRLDC
QCA **with no ERLDC approval**, and the assignment was **invisible to ERLDC** (the read paths are
region-scoped, but the assignment write path was not). The owned-plant variant likewise enqueued a
cross-region transfer request. The read/write asymmetry (list is region-scoped, assign is not) is the
tell.

**Impact:** A regional admin could pull any other region's RE plant under one of their own QCAs,
producing cross-region ownership that the owning region cannot see or govern — a region-isolation
breach and a data-integrity hazard.

**Reproducibility:** Always (pre-fix).

**Fix:** [server/routes/users.js](server/routes/users.js) — both `POST /:username/assignments` and
`POST /transfer-requests` now load the plant's `region` and reject (403) when the caller is not the
national admin and the plant's region ≠ the caller's region. Re-verified: the same call now returns
**403**, and every legitimate same-region assignment/transfer still works.

**Evidence:** `P8/assign-xregion` (now PASS), plus the direct probe showing pre-fix `201 Assigned`
with the ERLDC side blind to it.

### BUG-2 — Pre-deployment transfer-simulation oracle aborts on every run
- **Severity:** MEDIUM  ·  **Area:** Tooling / release safety  ·  **Status: FIXED & re-verified**

**Preconditions:** None — reproducible from a clean checkout.

**Steps to reproduce (pre-fix):** `node server/scripts/simTransferConflicts.js`.

**Expected:** The six-scenario correctness proof runs and reports pass/fail (its stated purpose is to
prove the transfer-conflict rule before deployment).

**Actual (pre-fix):** `SIMULATION ABORTED (unexpected error): bind message supplies 4 parameters, but
prepared statement "" requires 3`. The `seedDiscrepancy` helper passed 4 bind values to a 3-parameter
`INSERT` and never populated `wbes_acronym`, so the script threw before any scenario ran. Confirmed
present in the committed `HEAD`, so the oracle has been non-functional — the safety net that is
supposed to catch transfer regressions never executed.

**Impact:** False confidence: a "simulation passes" gate that cannot pass (or fail) — silent loss of
pre-deploy verification for the most sensitive logic in the system.

**Reproducibility:** Always (pre-fix).

**Fix:** [server/scripts/simTransferConflicts.js](server/scripts/simTransferConflicts.js) — the insert
now lists `wbes_acronym` and uses a matching 4-placeholder value list. Re-verified: **20/20 checks
pass.** (The shared projection logic was also extracted into
[server/utils/simulation.js](server/utils/simulation.js) so the oracle and the new Simulation screen
run identical arithmetic.)

### BUG-3 — Duplicate pending transfer requests accepted
- **Severity:** LOW–MEDIUM  ·  **Area:** Transfers  ·  **Status: FIXED & re-verified**

**Preconditions:** An RE plant owned by a QCA; a second QCA to receive it.

**Steps to reproduce (pre-fix):** Submit the identical transfer request twice
(`POST /api/users/transfer-requests`, same plant → same target → same effective date), or trigger the
transfer twice via `POST /:username/assignments`.

**Expected:** One pending request per (plant → target); a second identical submission should be
refused or coalesced.

**Actual (pre-fix):** Both submissions returned `201`, creating two identical `Pending` rows.

**Impact:** Duplicate approvals for one logical move; admin-queue clutter; risk of a second approval
re-applying the close/open on already-moved assignments.

**Reproducibility:** Always (pre-fix).

**Fix:** [server/routes/users.js](server/routes/users.js) — a `hasPendingTransfer(acronym, toUser)`
guard now rejects a second pending request for the same (plant, target) with a 409 in all three
transfer-creating paths (owned-plant transfer, unowned-plant claim, and the direct transfer-request
endpoint). Re-verified: the second submission now returns **409**.

## 6. Workflow Findings (what was verified)

- **Authentication / sessions:** login (OTP-bypassed → token), wrong-password and unknown-user both
  return `200 {success:false}` (no leak), logout revokes the token (`jti`), a revoked/garbage/absent
  token → 401. ✔
- **OTP:** disabled only via the supported `bypass_2fa` admin mechanism; every test account logs in
  with `requiresOTP:false` afterward. ✔
- **Regions:** create (201 + first admin), duplicate → 409, acronym rule (2–10 alnum) → 400,
  required-field → 400, rename/suspend → 200, invalid status → 400, **no delete route** (by design),
  unknown region → 404. ✔
- **Region isolation & hierarchy:** a regional admin sees only its own users; a cross-region username
  is rewritten into the caller's region; cross-region writes → 403; a regional admin cannot create
  regions or admins; the national admin cannot create ordinary USER/QCA. ✔
- **WBES upload:** valid import, duplicate-in-file skip, missing-name / invalid-region /
  suspended-region / bad-acronym / blank-row skips (each with a clear reason), header-only → 400,
  wrong file type → 400, re-upload upserts, non-superadmin → 403, and the **real 4166-row file loads
  cleanly**. ✔
- **Registration:** self-register → pending (no login before approval), admin approval creates the
  account, reject-without-note → 400, cross-region approve → 403, duplicate/invalid → 409/400,
  already-processed → 400, **EMBEDDED_IN_STATE gate → 403**. ✔
- **QCA management:** RE-and-`qca_name` enforced, QCA-to-QCA isolation, region-scoped plant visibility. ✔
- **Plant assignment:** direct admin assign, non-RE → rejected, duplicate → 400, non-QCA target → 403,
  blocked plant → 403, cross-region → **403 (after fix)**, ownership visible with `current_owner`. ✔
- **Discrepancies:** Net-Schedule-file rule enforced, filing window (`maxDays`) enforced, future date
  rejected, QCA can only file for a plant it holds, non-RE → 403, bad time-blocks → 400, filer/region
  visibility isolation. ✔
- **Transfers (core):** conflict **on** the discrepancy date → 409; **before** effective (discrepancy
  after) → 409; **after** effective (discrepancy strictly before) → allowed; ownership split
  `outgoing → eff−1`, `incoming → eff` with no gap/overlap; **double-approve guarded**;
  **approval-time re-check** blocks with state intact; same-day and future-dated transfers work. ✔
- **Return:** reverse transfer boundary correct. ✔
- **Cross-RLDC trade:** an ERLDC↔SRLDC trade is visible to **only** the buyer and seller regions, not
  the three uninvolved regions; a non-Traders account cannot carry trade fields (400); uninvolved
  region cannot consent (403); buyer consents (200) → seller resolves (200). ✔
- **Permissions matrix:** SUPERADMIN / ADMIN / QCA / USER positive and negative cases across regions,
  users, logs, registrations, qca-status, config read/write, discrepancy process, and simulation — all
  correct. ✔
- **Effective dates / timezone:** boundary arithmetic (`eff−1`) is consistent under the server's local
  time (IST); date columns returned as plain `YYYY-MM-DD`. ✔

## 7. New feature — Simulation screen

Built as requested so longer projections can be explored from the UI (not just the 6-case CLI oracle).

- **Backend:** [server/routes/simulation.js](server/routes/simulation.js), mounted at
  `/api/simulation` (auth + admin, region-scoped).
  - `GET /context` — the region's RE plants and QCAs for the pickers.
  - `POST /project { fromDate, toDate, acronyms?, whatIfTransfers? }` — per-day plant→QCA ownership
    across the range (≤366 days), plus optional what-if transfers evaluated with the **same**
    `findTransferConflicts` / approve logic the live routes use. What-ifs run inside a
    `BEGIN…ROLLBACK`, so the projection **never persists** — proven by an identical assignment-table
    hash before and after a run.
  - Shared engine extracted to [server/utils/simulation.js](server/utils/simulation.js), imported by
    both the endpoint and the (now-fixed) CLI oracle.
- **Frontend:** [src/components/SimulationScreen.jsx](src/components/SimulationScreen.jsx) — a
  "Simulation" tab (Navbar → AdminDashboard) with date range, plant selection, a what-if transfer
  builder, a per-plant ownership timeline (baseline vs after-what-ifs), and a conflicts panel.
- **Verified:** admin-only (QCA → 403); 30-day matrix correct (RESOLAR1: QCA-A through 09-09, QCA-B
  10–19, QCA-A from 20 after a transfer-and-return); clean what-if allowed, conflicting what-if
  blocked with the business message; out-of-scope plant → 403; non-persistence confirmed. `npm run
  build` and lint clean.

## 10. Where I got stuck, what worked, what failed, and the most likely genuine bugs

- **Where I got stuck:** nothing hard-blocked the run. Two friction points: the discrepancy filing
  required a correctly-named `NetSchdReportSummary@…` attachment (handled by uploading a properly-named
  file through the normal upload endpoint), and a couple of harness field-name mismatches (consent used
  `decision`, not `consent`) which I corrected — the product was right in both cases.
- **What worked:** essentially the whole system — auth, isolation, hierarchy, WBES upload, registration
  + gate, QCA/plant workflows, discrepancy rules, and especially the transfer conflict/ownership/return
  logic and the cross-RLDC trade visibility. 155/157 checks passed; the 2 "failures" are harness
  expectations, not defects.
- **What failed:** three genuine defects — a **cross-region plant assignment** hole (HIGH), a
  **non-functional pre-deployment simulation oracle** (MEDIUM), and **duplicate pending transfer
  requests** (LOW–MED). All three are fixed in this working tree and re-verified by a full clean re-run.
- **Most likely genuine application bugs (ranked):** (1) cross-region assignment/transfer — a real
  isolation breach with data-integrity impact; (2) the broken sim oracle — a real release-safety gap;
  (3) duplicate pending transfers — real but low blast radius. Everything else observed was either
  correct behavior or a test-harness artifact.
